## 一、界面工程（都是踩出来的）

### 1.1 「设置改了但页面没变」= 静默失效，两个来源
1. **页面/VM 必须订阅偏好，不能只在 `load()` 里读一次**。课表页有「已是 Ready 就直接 return」的短路，
   而锚点只在 `load()` 里读一次 → 校准页三处证据（界面 / prefs / 日志）全对，课表页纹丝不动。
   正确做法：VM 里订阅 `settings.prefs`，值变了**就地重算派生状态**（锚点与网络无关，不该为了重算
   再打一遍接口）。守卫只比 `monday` + `source`，**不比 `savedAt`**（写入每次都盖新时间戳，比它会让
   「自己刚写的值」被当成「用户又改了一次」白重算一遍）。
2. **`Dispatchers.Main.immediate` 上写 StateFlow 会同步唤醒订阅者 → 嵌套重入写入**。
   `_prefs.value = next` 之后订阅者可能反手又写一次偏好，此时 `next` 已过期；若落盘写 `next` 就会把
   订阅者刚写的值覆盖回去。实测点「清除」后内存 `2026-08-31|exam`、磁盘被写成 null → 下次冷启动锚点
   凭空消失。**落盘一律写最新的 `_prefs.value`**。副作用：日志顺序会交错（嵌套的日志排在外层前面），
   不要据日志先后推断事件先后。

### 1.2 配置一律单例 + StateFlow
`SettingsRepository` / `SessionRepository` / `RushStore` 都是全局单例 + StateFlow，位置变化不影响订阅
（主题在 Activity 顶层、尺寸在课表页，各订阅一次）。**各建实例 = 「点了深色没反应，只有重启才生效」。**
- 偏好键**存字符串**（`system`/`light`/`dark`），不存枚举序号 —— 以后插模式不会把旧值读成另一个模式。
- 尺寸档：高度 52/58/64/70/76（默认 64）、列宽 62/68/74/80/86（默认 74），读入一律 `snap()` 吸附
  （容错旧值/脏值；距离相同取较小档）。
- **尺寸只有一个来源**（`TimetableSizeSpec` + `TimetableSize` 推导 pitch/字号/块位置），渲染与自检
  看同一份公式 → 不会出现「格子变了、字号没变」。设置子页的「实时预览」直接调课表真渲染器
  （`ui/timetable/TimetableCanvas.kt` 的 `WeekTable`）；预览高度是**算出来的**（`span×max(pitch)−gap`）。

### 1.3 课表行高：真空隙，不是「行高 = pitch」
底纹格与节次轴 = 每行 `periodHeightDp` + **`Arrangement.spacedBy(PERIOD_GAP)` 的真空隙**，
**不是**「行高 = pitchDp（行尾空隙算进行内）」。两种写法总高 / 轴总高 / 块底边落点全都相同
（所以只看外框的断言抓不出问题），但**可见矩形差一个 PERIOD_GAP** → 后者让每个课块底边下漏 3dp 底纹。
内缩量 `TimetableSizeSpec.CELL_INSET_DP`（底纹格与课块共用）。
**渲染侧「对齐」有外框与可见矩形两种口径**：只断言外框（如「块底 == rowBottomDp」）会放行整类缺陷；
凡涉及相邻元素贴边，必须比**内缩之后**的矩形。

### 1.4 课表滚动（两条都是踩出来的）
1. **节次轴必须跟内容一起纵向滚**。轴「固定不滚」时滚到下半段，第 7 节的行下面对着轴上的「5」
   —— 数字与内容错位，比看不见节次号更糟。做法：轴与网格放进**同一个纵向滚动容器**。
2. **横向与纵向要用父子嵌套容器，不能叠在同一个 Modifier 链上**。实测
   `.horizontalScroll(h).verticalScroll(v)` 叠在同一个 Row（且共享 state）时手势方向判定出错：
   横滚到右侧后上下滑纹丝不动，横向位置还被重置回周一。改为外层纵滚、网格内层横滚。
3. 表头纵向固定、横向与网格**共享同一个 ScrollState**（各用各的必然标题错位）；列宽 74dp、单节高 64dp
   —— 列宽固定后 7 列装不下，横向滚动是必需。
4. 尺寸可读性口径：手机窄列 40~50dp 时课名只能挤三四个字 → 别用 weight 均分 7 列。

### 1.5 深色配色不能靠「压暗浅色底」
浅色底是近白粉彩（三通道差异极小，有意为之）。压暗后十个颜色塌缩成一批深灰、肉眼分不出。
正确做法 = `mix(surface, accent, 0.35)` 从饱和 accent 混。量化口径（最小两两距离 ×1000）：
浅色 25 / 旧深色 **5** / 新深色 **39**（`ui/timetable/CoursePalette.kt` 带变异探针自检）。
- 判断深浅用 `colorScheme.background.luminance()`，**不要用 `isSystemInDarkTheme()`**
  （本应用允许强制深色，系统偏好与实际配色可以不一致）。
- 中性色恒定、只有强调色跟色相走；`surfaceTint` 必须显式 `Transparent`。
- **M3 baseline 是紫色的** —— `lightColorScheme()` 没传的角色会落回 `#6750A4` 系
  （踩过：底部导航栏永远淡紫，切任何主题它都不变）。

### 1.6 Kotlin 零警告的两个坑
- `"第$n周"` 里的「周」是合法标识符字符 → 被当成变量名（要写 `${n}`）。
- 智能转换让 `!fitsTerm && x != null` 报 `Condition is always 'true'`（`fitsTerm` 的定义里已蕴含
  `x != null`）→ 直接写 `!fitsTerm`。
- 改完 grep `\p{Han}` 与 `^w:` 复查。

## 二、分享 / 导出 .ics（2026-09-21 实测）

### 2.1 预检查询只能证伪、不能证实
想「先查有没有 App 能处理、没有就别说文件没生成」——两个坑都在这个查询上：
1. **`ChooserActivity` 会吞掉唯一候选**。MuMu 上导出一直弹系统「沒有應用程式可執行這項操作。」，
   但同一台设备 `am start -a android.intent.action.SEND -t text/calendar` **能正常解析并打开**
   `com.google.android.gms/nearby.sharing.send.SendActivity`。同一 intent：AMS 能解析、选择器说没有。
   → 改成**单候选直投、多候选才套 `Intent.createChooser`**（只有一个 App 能处理时本来也没有「选」的
   必要，这也是 Android 12 之前的行为）。改完处理者真的打开了，裸报错消失。
2. **Android 11+ 包可见性过滤**：不声明 `<queries>` 时 `queryIntentActivities` 恒为空 ——
   那会在**真有日历 App 的真机上反过来谎报「没有能打开 .ics 的应用」**。已按
   `SEND` + `text/calendar` 声明。这条比坑 1 隐蔽：MuMu 上「表现正常」（本来就该显示"没有"）。
   查询要带 `MATCH_DEFAULT_ONLY`，与 chooser 的解析口径对齐。
3. 候选逐个写进 `JxauLog`，App 内诊断页直接可查。

### 2.2 ICS 其它硬约束
- `UID` 必须是**短 ASCII 形态**：`exam-{学期码}-{课程代码}-{yyyyMMdd}-{HHmm}@jxau.tools`。
  第一版把「学期码 + 中文课程名」整体 `%XX` 转义 → 200 字符、**被折成三行**。UID 只用于去重、
  不是给人看的 → 只取本来就有 ASCII 形态的字段，课程代码缺失才退回课程名。
- 折行按 **octet**（75 字节）且**不能劈开 UTF-8 多字节**（切点落在续字节上就往前退）；CRLF；
  转义 `\` `;` `,` 换行（`\r` 直接丢）；`DTSTART` 用 **UTC**（中国无夏令时，避开 `VTIMEZONE`）。
- 时间解析：`KsSj` 里是 `晚上7：00-9：00` —— ⚠️ **全角冒号**必须收；中文时段词（`上午/下午/晚上/…`）
  要按「开始时刻之后」的位置找，否则 `上午11：00-1：00` 会把结束时刻算成 01:00。

## 五、周次锚点体系（服务端不给开学日期）

### 5.1 为什么只能靠「反向校准」
- 教务内**没有第二个可信日期源** —— 7 处候选（课表/考试/成绩/教学计划/学期列表…）逐个实测排除。
- 学期初的考试安排里**只有补考**（期末考要到期末才排）→ 有补考的同学能反推出开学日期，
  **没挂科的同学拿到 `Data:[]`，推不出来。这是学期初的常态，不是边缘情况。**
- `Kszhou` 还可能是文字 `未定`（实测期末 6/16 条）→ **整条跳过**；
  `Ksday` 是 `2026-9-11` **不补零**形态，ISO 解析器吃不下，要宽容解析。
- 详见 `docs/教务系统接口清单.md` §4.2.1 与 `tools/probe_exam_api.py`。

### 5.2 落盘形态与优先级
- `TermAnchor` = `2026-08-31|manual|时间戳`，**单条、不按学期分组** ——
  分组会引入「当前学期是哪个」这个得同步的隐藏状态。脏值 / 认不出的来源一律 decode 成 `null`，
  **不猜日期**。
- 用户填的是**「现在第几周」**（不是开学日期）：`anchor = mondayOf(今天) − (N−1) 周`。
  先归周一再减 → 同周内周一周五周日填同一个数结果相同。
- 优先级 **手动 > 考试反推 > 缓存里的考试反推值**；手动与考试不一致时**两个都显示**。
- `TodayPosition` 四相位 `BEFORE / IN_TERM / AFTER / UNKNOWN`；`todayWeek: Int?`，
  **null = 算不出来，绝不兜底成 1**（否则界面把「不知道」显示成「第 1 周（本周）」）。
- **`anchorFitsTerm`**：锚点是单条的，而学期选择器能翻到十几年前 → 用当前学期的锚点渲染历史学期
  会报出**自信的错日期**（实测 `20242` 被写成「第 4 周（本周）9月21日 - 9月27日」）。
  判据只比**学年 + 上下半学期**，不猜具体日期；学期码形态不符时返回 `true`（拿不准就不改行为）。
  对不上 → 按「不知道」处理，文案说「切回当前学期即可」，**不是**「请去校准」（后者把人引错地方）。

## 七、开机广播与闹钟重建（2026-09-22 真机实测）

### 7.1 ⚠️ `am force-stop` 会把包推进 stopped 状态，而 stopped 的包**收不到 `BOOT_COMPLETED`**
这是既定行为（`FLAG_EXCLUDE_STOPPED_PACKAGES`），不是 bug。踩的姿势：
为了「干净地」构造前置条件先 `force-stop`，然后重启 —— **日志一条不出、闹钟一个没有**，
看上去完全像功能坏了。
- 构造前置条件要停进程时用 **`am kill`**（只杀后台进程，不动 stopped 标志）；
- 判据：`dumpsys package <pkg> | grep -o 'stopped=[a-z]*'`。
- **这条对真实用户也成立**：被强停过的 App，重启后不会自己把闹钟补回来，
  要等用户下次打开（`MainActivity.applyAlarms()` 兜底）——「App 启动是唯一一定会发生的事件」
  这个兜底设计因此是必要的，不是冗余。

### 7.2 验证「重启后闹钟还在」必须证明「App 没被启动过」

### 7.4 ⚠️ 删掉接收器 ≠ 闹钟消失：必须主动 `cancel`，否则留下幽灵闹钟

**现象**：把「每日课程提醒」连同 `DailyCourseAlarmReceiver` 一起删掉、装上新包之后，
`dumpsys alarm` 里那颗闹钟**还在**（`RTC_WAKEUP … DailyCourseAlarmReceiver`）。
它到点会触发一次，而接收器已经不存在 → 日志里留下一条 `Unable to start receiver`。
**用户每跨一次版本就多留一颗。**

**原因**：**`AlarmManager` 里的闹钟不随包更新消失**。它是系统进程持有的 `PendingIntent`
（`PendingIntentRecord`），跟 Manifest 里的 `<receiver>` 声明是两回事 —— 删声明不会回收它。

**修法**：新版本在启动兜底路径里主动撤销（`MainActivity.cancelLegacyReminderAlarm()`）：

- 用**旧版本的请求码 + 组件名字符串**造一个等价 PendingIntent：
  `PendingIntent.getBroadcast(ctx, 4202, Intent().setClassName(ctx, "…DailyCourseAlarmReceiver"), …)`
  再 `alarm.cancel(...)`；
- 类已被删除**不影响构造** —— 组件名在**发送广播**时才 resolve；
- PendingIntent 的相等性只看 `requestCode` + `Intent.filterEquals()`（action / data / type /
  component / categories），**`extras` 不参与匹配**，所以 `FLAG_UPDATE_CURRENT` 不会妨碍匹配；
- 请求码必须与当年一致，写错一位就**静默失败** —— 幽灵闹钟继续留着，且没有任何报错。

**⚠️ 判据本身有个坑**：`dumpsys alarm | grep -c DailyCourseAlarmReceiver` **会数错**。
dumpsys 的输出里同时有 **pending 列表**（`RTC_WAKEUP #NN: Alarm{…}`）和
**每 uid 的历史记录**（`[tag=… reason=… elapsed=…]`），而**撤销成功后历史里反而多一条**
`reason=alarm_cancelled` —— 于是 `grep -c` 从 1 变成…还是 1，看起来像"没生效"。

- 正确判据：只看 pending 区段（带 `Alarm{` / `RTC_WAKEUP #` 的条目）；
- 或反向用「历史里出现 `reason=alarm_cancelled`」当**撤销确实发生过**的正证据。
- 这次就是先被那个 `1` 骗了一下，差点误判成撤销失败。**判据要精确到区段，不能 grep 整个 dump。**

### 7.5 ⚠️ `LOCKED_BOOT_COMPLETED` 里读不到 `shared_prefs` —— 别声明它

**现象**：`BootReceiver` 同时声明 `LOCKED_BOOT_COMPLETED` + `BOOT_COMPLETED` 时，两次重启表现不一致：
12:06 那次 `restorePending` 读到落盘时刻、补排成功；13:18 那次同样收到广播，却**静默什么都没做**。
日志只有「收到 …LOCKED_BOOT_COMPLETED，重新排入抢课闹钟」，之后 `restorePending` 的
**三个分支一个都没进**（既没有「发现未执行的抢课定时」，也没有「已经过去，不再补排」）
→ 说明它拿到的 `rushTriggerAt == 0`（`if (at <= 0L) return` 是唯一的静默返回）。

**原因**：`LOCKED_BOOT_COMPLETED` 在 **direct boot** 阶段投递，那时
`/data/data/<pkg>/shared_prefs/`（credential-encrypted 存储）**还没解锁**，
`getSharedPreferences()` 拿到的是一份**空数据**（不抛异常，就是读不到）。
解锁后的 `BOOT_COMPLETED` 里同一份代码能正常读到 →
**同一条代码路径的成功/失败取决于「解锁」与「广播」的先后，是竞态。**

**怎么判别是「读不到」而不是「写丢了」**：重启后 `run-as cat shared_prefs/jxau_cache.xml`,
**仍然是注入值** → App 从未成功读到过（而不是读到后被覆盖）。
再加上「三个分支一个都没进」，就能定位到 `at <= 0` 那条静默返回。

**修法**：**不要声明 `LOCKED_BOOT_COMPLETED`**，只留解锁后的 `BOOT_COMPLETED`。

- 抢课依赖**已登录的会话**，而会话（`jxau_session`）同样在 credential-encrypted 存储里 →
  在 direct boot 阶段排这个闹钟**没有任何意义**，早那几秒换不来任何东西；
- 代价却很大：等于把竞态引进**唯一的自我修复路径**，而它的失效形式正是「静默」。
- `MY_PACKAGE_REPLACED` / `TIME_SET` / `TIMEZONE_CHANGED` 不受影响（都在解锁后投递）。

> ⚠️ **方法论**：这条是先 PASS 过一次（12:06）、清理重跑才 FAIL（13:18），
> 差点被当成「重构引入的回归」。
> **时序相关、只通过一次的用例不算通过** —— 要么多跑几次，要么像这样把依赖的时序条件
> 从设计里直接去掉。这次的正确结论不是"再跑一遍看运气"，而是"这个声明不该存在"。

### 7.6 ⚠️ 验收脚本自己也会制造假失败：别一看到标志日志就返回

**现象**：手动复现（注入 → `reboot` → 轮询 `sys.boot_completed` → 抓全量日志）**完全通过**
（`发现未执行的抢课定时，重新排入闹钟` + `已设定抢课定时触发：…` + pending 列表里确有该闹钟），
而 `tools/verify_boot_restore.py --rounds future` 报 `FAIL 重启后抢课闹钟已重建：未找到`。

**两处假失败的来源（都是采集方式的问题，不是被测代码）：**

1. **一看到标志就 return**。原 `reboot_and_collect` 在 `"BOOT_COMPLETED" in buf` 时立刻返回，
   而那条日志只是「**收到广播**」；`restorePending` 的结论（`发现未执行的抢课定时` /
   `已设定抢课定时触发` / `已经过去，不再补排`）在它**后面几毫秒**才打 →
   脚本在闹钟排上之前就去查 `dumpsys alarm` 了。
2. **`alarms()` 的配对方式**。原来是分别 `findall`「含 `Alarm{` 的行」与「含 `tag=` 的行」再 `zip`。
   但 `dumpsys alarm` 里每个 uid 还有一段**历史记录**（`[tag=… reason=… elapsed=…]`），
   那些行的 tag 同样形如 `tag=*walarm*:本包/.service.X`，**也会被 findall 抓到** →
   两个列表长度不等 → `zip` 静默截断/错位，把「有闹钟」判成「没有」。
   （§7.4 里 `grep -c` 的误判是同一个坑的另一种表现。）

**修法**：① 查之前先等 `sys.boot_completed=1`；
② 抓到 `BOOT_COMPLETED` 后**再等几毫秒**，以 `restorePending` 的**结论行**为准；
③ 闹钟解析必须**成对匹配**（`Alarm{…}` 行 + 紧随的 `tag=` 行），历史记录一律不认。

> **教训**：**假失败和真失败一样有害** —— 它会让人去"修"没坏的东西
> （这次差点把 `PendingTaskStore` 的读写逻辑重新翻一遍）。
> **验收工具自己的输出也要能被检验**：当脚本结论与手动复现冲突时，
> **先怀疑采集方式，再怀疑被测代码**。

### 7.7 ⚠️ Android 11+ 连 root 也不能改第三方包的**组件级**启用状态

> 想只关掉 `BootReceiver` 一个组件？**做不到。** 退成包级 `pm disable <pkg>` 同样不行 ——
> 前置能过，但**不跨重启保持**，见 §7.8。

**现象**：变异探针（第 3 轮）想验证「重启后闹钟确实由本包重建」，做法是

```bash
adb shell pm disable-user cn.edu.jxau.tools/cn.edu.jxau.tools.service.BootReceiver
```

结果抛 `java.lang.SecurityException: Shell cannot change component state for
cn.edu.jxau.tools/cn.edu.jxau.tools.service.BootReceiver to 2`，
且 `dumpsys package <pkg>` 里连 `Disabled components:` 这一段都不出现 —— 组件根本没被记下来。

**根因**：Android 11（API 30）起收紧了 shell/root 的权限边界 ——
**只允许改自己包的组件状态**，第三方包的组件级 enable/disable 一律拒绝（root 也不例外）。

**第一次修法（不成立）**：既然组件级不行，就退成**包级** `pm disable <pkg>`（root 下可用）：

```python
dev.raw("root"); time.sleep(6); dev.connect()   # 先 root，否则 pm disable 也没权限
dev.sh("pm disable %s" % PKG)
check(PKG in dev.sh("pm list packages -d"), "前置：包已被禁用（`pm list packages -d` 里能看到）")
```

参数换成包级（组件级写 `<pkg>/<comp>`，包级只写 `<pkg>`），**前置断言也通过了**。
但这一轮仍然拿到假失败 —— 因为**包级禁用在这台机器上不跨重启保持**，见 §7.8。

> **教训**：写变异探针**先确认「前置条件真的成立了」再往下跑**。
> 这次原来的脚本在第 3 轮直接报 `FAIL 前置：BootReceiver 已被禁用`，
> 那是探针自己没生效 —— 如果只写 `check(不是期望结果)` 而**不单独断言前置**，
> 就会得到一个"看起来证明了因果"、实际上什么都没关掉的假证据。
> 前置断言不是啰嗦，它是**变异探针的唯一支柱**。
>
> **但还要再进一步**：前置成立 ≠ 变异在**重启之后**仍然成立。
> 凡是「设状态 → 重启 → 看现象」的探针，**状态必须在重启后重新断言一次**，
> 否则你测的是「重启把状态抹平了」这件事，而不是被测代码。

### 7.8 ⚠️ 平台级变异在本机 MuMu 镜像上不可用：变异必须落在**编译产物**里

**现象**：`-` 组件级 `pm disable-user <pkg>/<comp>` —— Android 11+ 直接拒（§7.7）；
包级 `pm disable <pkg>` —— **前置通过（禁用成功），重启后禁用被抹掉**：
`pm list packages -d` 里本包**没了**，`dumpsys package` 里 `enabled=1`，
`/data/system/users/0/package-restrictions.xml` 里的本包记录也消失。
于是开机时包是**启用**的，接收器照跑，探针以为「代码没坏但因果没被证明」。

**怎么排除「其实是我没禁用成功」**：两次独立复现，每次都在
`pm disable` **之后、重启之前**单独断言 `pm list packages -d | grep jxau` 有本包（前置 PASS），
重启后再看同一命令 —— 空。两次结果一致。现场同时有：`dumpsys alarm` 里那颗闹钟的
`origWhen` **正是注入值**、日志里 `已设定抢课定时触发：…`、而 `/proc/uptime` 只有 **34 秒**
（证明设备**确实重启过**，不是我误判了现象）。

**还有一层坑把第一次实验污染了**：`adb reboot` 之后 **adbd 会掉回 shell**，
若脚本不在**每次操作前**重新确认 root，`pm disable` 会**静默失败**（不抛异常、只是没生效）
→ 先写出一个「禁用成功」的假前置，再得出「重启后闹钟还在」的假因果。
**结论：任何需要 root 的真机脚本，root 必须在每次操作前自证**（`id` 里有 `uid=0`），
不能只在开头 `adb root` 一次。⚠️ 但**也别无条件 `adb root`** ——
MuMu 的 adbd 默认就是 root，`adb root` 只会平白重启一次 adbd；紧接着 `adb reboot`
的组合会把实例搞成 `offline`（连 `MuMuManager` 都报 `player_started` 但 adb 握不上手），
今天为此付出了两次恢复时间。正确姿势是**先看 `id`，不是 root 才升级，升级后必须重连**：

```python
def ensure_root(self):
    cur = self.sh("id")
    if "uid=0" in cur: return cur     # 已经是 root，别动 adbd
    self.raw("root"); time.sleep(8); self.connect(); time.sleep(3)
    return self.sh("id")
```

**可行修法：变异落在编译产物里。** 变异点是清单里
`<receiver android:name=".service.BootReceiver">` **整块**，注释掉重新构建安装即可，
代码一行不用改（「改回去」因此没有残留风险）。前置由脚本自己查证：
`cmd package query-receivers -a android.intent.action.BOOT_COMPLETED` 里**查不到本包**，
这一条**单独断言、不许省** —— 没有它，「重启后没闹钟」既可能是「代码坏」也可能是
「探针没生效」，两者分辨不出来。结果：**mutant 轮 6/6 通过**，因果闭合。

**顺带的坑：XML 注释里不能出现连续两个减号。** 变异注释第一版里写了命令行参数原文
（含 `--`），清单直接解析失败、构建报 `Error parsing …`。注释里**别写 `--xxx` 风格的原文**。

流程图见 `tools/verify_boot_restore.py` 的 `round_mutant` 文档串。
