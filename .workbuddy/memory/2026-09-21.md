## 主题色系统 + 课表空格底纹（提交 887dcbc）

### 结构：色相 × 明暗两个正交维度
`ThemeMode`（跟随系统/浅色/深色）管深浅，新增 `ColorTheme`（经典蓝/青碧/竹青/紫罗兰/玫红/暖橙）
管颜色，六乘三自由组合。枚举只放 `key`/`label`（data.model 不引 Compose），
种子色与派生规则在 `ui.theme.ColorThemeSpec`。新键 `color_theme` 存字符串，脏值回退默认。

### 派生：按目标相对亮度反解明度，不是按 HSL 的 lightness
一个种子色取色相/饱和度 → 二分（后改扫描）反解明度使**相对亮度**落在目标上 → 八个角色。
浅色 primary 目标亮度 0.145（白字对比 ≈5.4）、容器 0.820、容器字 0.030；
深色 primary 0.450、容器 0.085、容器字 0.720。
**第一版的坑**：按固定 HSL 明度（浅色一律 L=0.36）写，青碧色的 primary 变成 `#00B8A1`，
白字对比只有 **2.51**（不可读）。HSL 的 lightness 不是感知亮度，同为 0.36 时青色比蓝色亮得多。
改法后六主题白字对比齐平：浅 5.37+ / 深 7.11+（每类角色取六主题最差）。

### 教训：浮点反解 + 8 位量化 → 两个平台落到相邻台阶
自检第一版用**二分**反解明度，真机 FAIL **5 项、偏差高达 70/1000**（远超 Float32 精度误差）。
根因：二分收敛到「目标亮度的浮点位置」，颜色再量化到 8 位时，台阶边界附近 Kotlin(Float32)
与 Python(float64) 各自四舍五入到**相邻的两档**（相对亮度 0.82 处，1/255 的差 → 对比度差 70）。
**定位方法**（很值得复用）：FAIL 的项恰好全是含二分的（对比度/主题距离），
不含二分的（色相漂移、变异探针、底纹 12 项）全对 —— 这条线索直接把根因指到反解环节。
**解法**：改成在 [0,1] 上等步长扫描（500 步）、取「**已量化颜色**里亮度与目标差最小」的一档。
候选集合离散且两边完全相同，比较用的亮度差（~1e-7）远小于相邻候选亮度差（~1e-4），
选中项不再受计算精度摆布。改完真机与脚本逐项一致。
**残余口径**：断言给 ±1 的最小单位容差（Kotlin Float32 vs Python float64 的末位抖动），
精确到个位会在 1343.5 这种取整边界上产生**假 FAIL**，而假 FAIL 会让人开始无视断言。

### 顺手修的旧缺陷：M3 baseline 是紫色的

  用的 `surfaceContainer` 没传 → 落到 Material baseline（紫色 `#6750A4` 系）。
  切任何主题它都不变，主题看起来「只换了一半」。现在把 M3 1.3 会用到的颜色角色全部显式给出：
  surfaceContainer 五档（自表面层级派生）、surfaceDim/Bright、inverseSurface/OnSurface、
  inversePrimary（取反明暗的 primary）、outlineVariant、tertiary 对齐 secondary（不留紫色后门）。
- **`surfaceTint` 要设成 `Color.Transparent` 而不是 `primary`**：实测紫色主题下

  同一个界面里一半中性面染色、一半不染，反而显脏。中性面恒定是本项目既定策略
  （课表十色课程块是跟 surface 混色得到的，surface 一偏就得全部重调）。

### 课表空格底纹重做

## 修复「课块底边漏背景」（用户反馈：有课的色块高度小了一点，最底下有部分背景漏了）
（提交 `9de148a`）

### 根因：两种行高模型，总高相同、可见矩形差一个 PERIOD_GAP
`blockHeightDp` / `rowBottomDp` 是按「**行高 = periodHeightDp，行与行之间留 PERIOD_GAP**」写的，
但 `DayColumn` 的底纹列实现的是「**行高 = pitchDp**，把行尾空隙算进行内」（除最后一节外）。
两种写法：总高一样 `(n-1)*pitch + h`、轴总高一样、块底边落在 `rowBottomDp` 上也一样 ——
**既有的对齐断言全都放行**。差别只在**行的可见矩形**：后者多探出整整一个 PERIOD_GAP。
→ 每个课块底边之下露出 3dp 底纹填充。附带：旧写法下除最后一节所有格子高 67dp、
最后一节 64dp，格子之间本身就不一致。

### 改法
渲染侧改成与块高公式同一个模型：每行 `.height(periodHeightDp)` +
`Arrangement.spacedBy(PERIOD_GAP.dp)`（底纹列与节次轴都改）；内缩量抽成
`TimetableSizeSpec.CELL_INSET_DP`（底纹格与课块共用，写死的 `1.dp` 去掉）。
模型侧新增 `cellTopDp / cellVisibleTopDp / cellVisibleBottomDp / blockVisibleTopDp /
blockVisibleBottomDp / fitsCells`，把「课块可见矩形逐 dp 等于它覆盖的底纹格可见矩形」写成不变量。

### 方法论：只看外框的断言抓不住可见矩形缺陷
「块底边 == rowBottomDp(末节)」用**外框**比较，两种行高模型都满足 → 放行了这个 bug。
必须比**内缩之后的可见矩形**。断言要覆盖 5 档高度 × 11 起点 × 全部跨度（330 例穷举）。
变异探针：把旧行高模型的可见底边固化成「比课块底边低 PERIOD_GAP」，证明用例有判别力。

### 真机证据（`tools/measure_block_fit.py`，新）
逐像素量「课块底边下方还漏着多少底纹填充」：

- 修复后：26/26 段漏出 **0px**。
- 最干净的对照是**同行空格**：修复前「块底 855 / 同行空格可见底 861」差 3dp；
  修复后两者都是 855。且「块底→下一格顶」的背景空隙 10px 与空格之间的间隙 10px 完全一致
  = `1dp 内缩 + 3dp 空隙 + 1dp 内缩`（模型吻合）。
- 空列格间隙本身 4px → 10px（旧行高模型 vs 新）。块可见高不变（跨 2 节 258px）。
- 节次轴数字顺带对齐了：行高 = 单节高后，数字中心正好在行中线

## 周次校准已落地（提交 1bddf7f）：功能 + 验证时揪出的四个缺陷

用户拍板：校准内容 = **填「现在第几周」**；入口 = **我的 → 设置里加一项**（不是课表页就地可点）。

实现：`TermAnchor`（单条锚点落盘 `2026-08-31|manual|时间戳`）/ `WeekMath.anchorFromWeekNo` /
`positionOf` + `TodayPosition` 四相位 / `resolveAnchor`（手动 > 考试反推 > 缓存）/
设置页 `WeekAnchorPage`（± 调周次 · 设为当前周 · 清除）。

**验证阶段揪出的四个缺陷（都不是设计问题，是实现/接线问题）：**

1. **校准后课表页纹丝不动** —— `load()` 有「已是 Ready 就直接 return」的短路，
   而锚点只在 `load()` 里读一次。校准页三处证据（界面/prefs/日志）全对，课表页还说第 4 周。
   修：VM 里订阅 `settings.prefs`，锚点变了就地重算，不重新请求接口。
   守卫**只比 `monday` + `source`，不比 `savedAt`**（写入每次都盖新时间戳，比它会让
   「自己刚写的值」被当成「用户又改了一次」白重算一遍）。

2. **嵌套写入把磁盘写回旧值（最阴的一个）** —— `viewModelScope` 在 `Dispatchers.Main.immediate` 上，
   `_prefs.value = next` 会**同步**唤醒订阅者；订阅者反手又写一次偏好，外层随后拿**过期的 `next`**
   落盘，把内层刚写的值覆盖掉。实测点「清除」后内存 `2026-08-31|exam`、磁盘被写成 null
   → 下次冷启动锚点凭空消失。修：`mutate` 落盘写最新的 `_prefs.value`。
   **日志顺序会因此交错**（嵌套的日志排在外层前面），不要据日志先后推断事件先后。

3. **文案说错话**：(a) 同一句锚点说明在头部与警示卡里各渲染一遍，且长文案在头部换行会把
   「学期/本周」按钮挤下去 → 定死约定「卡片显示了头部就不重复」+ `maxLines=1`；
   (b) 考试安排没数据（用缓存兜底）时报「推算有分歧」→ 补 `examAnchor == null` 分支。

4. **拿当前学期的锚点渲染历史学期，报出自信的错日期** —— 学期选择器能翻到十几年前，
   而锚点是单条的。切 `20242`（一节课都没有）时界面写「第 4 周（本周）　9月21日 - 9月27日」。
   修：`WeekMath.anchorFitsTerm` 只比**学年 + 上下半学期**（不猜具体日期；学期码形态不符时
   返回 true，拿不准就不改行为）。对不上时按「不知道」处理，文案说「切回当前学期即可」
   而不是「请去校准」—— 后者会把人引到没用的地方（新增状态位 `anchorMismatch` 就是为这个）。

**踩到的两个编译坑**（都是 Kotlin 的「聪明」）：
- 智能转换让 `!fitsTerm && resolution.monday != null` 报 `Condition is always 'true'`
  （`fitsTerm` 的定义里已蕴含 `monday != null`）→ 直接写 `!fitsTerm`。
- 教训复用：`$n周` 里「周」是合法标识符字符会被当成变量名 —— 这次没再犯，grep `\p{Han}` 复查过。

**证据**：`tools/verify_week_anchor.py` 58/58 PASS（独立实现 8 个函数，不复用被测代码/常量）；
端上自检 教学周推算 93/93 + 周次锚点存取 17/17；编译零 `w:` 零 `e:`；
真机逐项对账截图 `tools/i2_manual_calibration_conflict.png`、`tools/i3_term_mismatch_unknown.png`。
